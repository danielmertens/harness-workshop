The harness

A harness is everything around the model.

The code that runs the steps, checks the result and decides. And the skills that tell the agent how your team works.

Four ideas for today

A small, generic harness. The repository configures it.

The model reasons, code decidesThe agent plans, writes and reviews. The order of the steps, the retries and the verdict are plain C#.
Every step is a skillThe harness has no prompts. Skills, the quality gate and work items live in the repository.
Feedback is an instructionA failing gate or review goes back to the agent, written for the agent that has to fix it.
Evidence lives with the workPlan, gate results, reviews and logs land in the work item folder, next to the diff.

Lab 1 · Why we start here

Running an agent is easy. Knowing what it did is the hard part.

The naive loopTwo prompts, then a commit. The agent decides when it is done. What is left for you: a diff, and the job of checking everything by hand.
What we build todayA loop where code decides when the work is done, sends problems back to the agent, and leaves evidence a reviewer can read.

Trust doesn’t come from a better model. It comes from the harness around it.

Lab 1 · 15 min

The naive loop

What

Run loop.cs as it is on T01: two prompts, then a commit. Look at the result like a reviewer.

Why

Before you improve anything, see what you actually know about a run. Usually: nothing, until you check by hand.

Goal

An answer to: who decided this was done, and on what basis?

Lab 2 · Why skills

How the team works belongs in the repository.

A prompt in C#Policy hidden in plumbing. To change how the team plans, you change the harness. Nobody reviews it, and a developer working by hand uses other instructions.
A skill in the repositoryVersioned with the code, reviewed in a pull request, and the same /plan for the loop and for a developer. The harness only names the step and the work item.

The harness decides the order of the steps. The repository decides how each step is done.

The same loop.cs can now drive any repository that has these skills.

Lab 2 · 20 min

Every step is a skill

What

Move the prompts out of C# into plan and implement skills in the repository. The loop gets the task file.

Why

A prompt in C# is policy hidden in plumbing. Skills are versioned, reviewed, and the same for a developer working by hand.

Goal

A loop.cs without a single instruction for the model.

Lab 3 · Why a quality gate

A deterministic check. Every change, every time.

The agent may forgetTo build. To run the entire test suite, not only the tests it just wrote. A check your team always does. And it can still say “all tests pass”.
The gate never forgetsAfter every implement step, code runs the build, the whole test suite and every other check that must always pass. Same checks, every time. The exit code decides.

We don’t trust the agent to remember. Anything that must always happen on a code change belongs in the gate, not in a prompt.

Build and test are only the start: the gate grows with every check your repository needs.

Lab 3 · 15 min

A quality gate the repository owns

What

quality-gate.ps1 in the repository: the build, the whole test suite and every other check that must always pass. The harness runs it after every implement step.

Why

A deterministic check. We don’t trust the agent to remember to build, to run the entire test suite, or any other check that must always run. Code runs them, every time.

Goal

Nothing is committed unless code says it is green, and the gate result is kept as evidence.

Lab 4 · Why feedback as an instruction

A failure only helps if the agent can act on it.

Raw outputRestore noise, absolute paths from the build machine, a stack trace. The agent has to guess what matters, and what it is allowed to change.
Output as an instructionOnly the signal, where to look, and what to do and what not. Code sends it back to /implement, as a file, for a limited number of attempts.

The gate’s output is the next prompt. Write it for the agent that has to fix it.

Bounded: three attempts, then the loop stops and a human takes over.

Lab 4 · 20 min

Feedback the agent can act on

What

Rewrite the gate output as instructions, and send it back to /implement: at most three attempts.

Why

A red gate only helps if the next attempt knows exactly what to fix. The gate’s output is the next prompt.

Goal

A loop that recovers from a failure on its own, and stops for a human when it can’t.

Lab 5 · Why an agentic review

The tests check what the tests check. A reviewer checks the rest.

What the gate can’t seeA requirement nobody wrote a test for. An error case that is not tested. A change outside the task. A test that would still pass if the feature broke.
A review that code can act onA fresh session reviews the change against task.md. A follow-up asks for the findings as JSON. Code reads the severities: high or medium goes back.

The model judges. Code decides, from data, never from prose.

What high, medium and low mean is written in the review skill: the repository owns it.

Lab 5 · 20 min

Agentic review

What

A review skill in a fresh session, then a follow-up that asks for the findings as JSON. High or medium goes back.

Why

The gate only sees what the tests see. Every requirement met? Error cases tested? Scope kept? That needs a reviewer.

Goal

A commit only after a green gate and a review with nothing high or medium.

Lab 6 · Why event logs

Trust what the loop did, not what the agent says it did.

The agent’s summary“Done, all tests pass.” A claim, written by the same agent that did the work. It leaves out what it tried, what failed and what it cost.
The event logEvery skill call, tool call, output and token, per step, in the work item folder, committed with the work. One line of code writes it.

If you can’t trace a run, you can’t improve it.

Lab 7 reads these logs to find where the loop itself is weak.

Lab 6 · 10 min

Observability

What

Write every event of every step as JSON lines in the work item folder, committed with the work. Ask the logs what each step cost.

Why

A record of what the loop actually did, not what the agent says it did. For tracing a run, and as input for Lab 7.

Goal

An event log for every step, as a standard artifact of every run.

Lab 7 · Why an improvement loop

Every mistake becomes a fix in the repository.

An agent reads the evidencePlans, gate results, reviews and event logs of past runs. It finds retries, findings the gate could catch, rules the agent pushed against, and proposes fixes.
People decideYou run /improve yourself, judge every proposal, and apply the ones you agree with as a normal pull request. The harness never changes its own rules.

This outer loop is how trust grows over time.

“Every time the agent makes a mistake, engineer a fix so it can’t make it again.” Mitchell Hashimoto, My AI Adoption Journey

Lab 7 · 20 min

The improvement loop

loop runs›evidence›you + /improve›your PR: skills, gate, hooks›better runs
What

An improve skill that reads the work item folders and proposes changes. You run it yourself, interactively.

Why

The evidence also shows where the loop itself is weak. Every mistake becomes a fix in a skill, the gate or a hook.

Goal

One improvement, backed by evidence and committed by you. The harness doesn’t change.

Wrap-up · and then a human looks

For your own repository, in this order

  1. Write down how your team works as skills: plan, implement, review. Commit them.
  2. Write the quality gate as a script in the repository. Make its output an instruction, not a log.
  3. Keep the harness small and generic: it calls skills and the gate, loops a few times, and decides.
  4. Put the evidence where the reviewer is: the work item folder, the branch, the merge request.
  5. Every time the agent gets something wrong, fix the skill, the gate or a hook.
