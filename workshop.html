Wrap-up Reference
The question

How do you trust an agent to work on its own?

Not by reading everything it does, and not by hoping. You build a development loop around the model: code decides the order of the steps, checks the result, sends problems back, and keeps the evidence. That loop is the harness.

The model reasons, code decidesThe agent plans, writes and reviews. The order of the steps, the retries and the verdict are plain C#.
Every step is a skillThe harness has no prompts. It calls /plan, /implement, /review. Skills, quality gate and work items live in the repository, owned by its developers.
Feedback is an instructionA failing gate or review goes back to the agent. Write that output for the agent that has to fix it, not as a log.
Evidence lives with the workPlan, gate results and reviews land in the work item folder, and travel with the branch to the human reviewer.

Where you start

About 55 lines of C# that plan, implement and commit. The prompts are hard-coded in the harness, and nothing checks the result.

Where you can end up

Over seven labs you grow it into a loop like this one. The orange steps are the model. The blue ones are yours.

the model reasonscode decidesoutside today's code
One possibility, not the answer

This is the loop we build today, and it is only one of many. The harness is plain code, so you can build any loop: add a step (a security scan, a design check), drop one, change the order, or retry on other signals. Shape it to how your team works.

Between runs

Every lab runs the loop on a work item, and every lab ends by undoing that run, so the next lab starts from your own work only: the skills and the gate you committed. We suggest T01 every time, so you can compare runs. Take T02 or T03 if you are curious; undo them the same way.

The loop commits on main (until menu A fixes that). So commit your own changes in app/ (skills, gate) before a run: then undoing the run never throws away your work.

Undo a run that committed:

git -C app reset --hard HEAD~1

Undo a run that stopped without a commit:

git -C app reset --hard
git -C app clean -fd

Lab 1 · 15 min

The naive loop

Before you improve anything, run what you have and look at it with the eyes of a reviewer.

  1. Read loop.cs. It is the whole harness: two prompts, two git commands, and a helper that opens an agent session in app/. Note PermissionHandler.ApproveAll: every tool call the agent wants is approved.

A run takes one or two minutes: time to read app/README.md and app/.workitems/T01/task.md, so you know what the agent was asked.

    dotnet run loop.cs T01

  4. Check it yourself. Run the tests:

    dotnet test app

    Then start the app, open http://localhost:5080 and try the dropdown:

    dotnet run --project app/src/Payroll

    Does the work meet task.md? How long did it take you to find out?

    git -C app reset --hard HEAD~1

Lab 2 · 20 min

Every step is a skill

Why

A prompt in C# is policy hidden in plumbing. Move the instructions into skills in the repository: versioned with the code, reviewed in pull requests, and the same for a developer working with Copilot by hand. The harness only says which step runs, for which work item. It calls a skill like a slash command: /plan .workitems/T01/task.md.

  1. Create the plan skill. A skill is a folder with a SKILL.md.

    app/.github/skills/plan/SKILL.md
    ---
name: plan
description: Writes an implementation plan for a work item. Use when invoked as /plan <task file>.
argument-hint: <task file>
---

# Plan a work item

The argument is the task file of a work item, for example `.workitems/T01/task.md`, written by a human.

1. Read the task file. Then read `AGENTS.md`, `README.md` and the code and tests that the task touches.
2. Write `plan.md` next to the task file, with these sections:
   - **Goal**: one or two sentences.
   - **Changes**: per file, what changes and why.
   - **Tests**: the unit tests to add, one line each. Include every example and every error case from the task.
3. Do not change any other file.

Reply with one line: the path of the plan.

  2. Create the implement skill. Write it yourself first; compare with this one afterwards.

    app/.github/skills/implement/SKILL.md
    ---
name: implement
description: Implements a work item from its plan. Use when invoked as /implement <work item folder>.
argument-hint: <work item folder>
---

# Implement a work item

The argument is a work item folder, for example `.workitems/T01`, with `plan.md`.

## Steps

1. Read `plan.md` in that folder.
2. Implement it: change the code and add the unit tests from the plan. Follow the style of the existing code.

## Rules

- Do not change `task.md`, anything under `.github/`, or `quality-gate.ps1`.
- Never delete, skip or weaken a test to make it pass.
- Do not commit. The harness does that.

Reply with a short summary: which files you changed and which tests you added.

  3. In loop.cs, stop hard-coding where work items live. Replace the line that sets id: the loop now gets the path of the task file, and everything else follows from it.

    loop.cs, instead of var id = args[0];
    var task = args[0];                           // the task file, relative to the repository: .workitems/T01/task.md
var workItem = Path.GetDirectoryName(task)!.Replace('\\', '/');  // its folder: every step writes its output next to the task
var id = Path.GetFileName(workItem);          // a short name, for the commit message

    Then replace the two Ask lines. No prompt text is left: only the step name for the console, a skill, and its argument. The plan skill gets the task file; the implement skill gets the folder and finds the plan there itself.

    loop.cs
    await Ask("plan", $"/plan {task}");
await Ask("implement", $"/implement {workItem}");

  4. Commit the skills. They are part of the repository now.

    git -C app add .github
git -C app commit -m "Add plan and implement skills"

  5. Run it on T01 again, so you can compare with Lab 1. From now on you pass the task file, relative to app/. In the tool list you now see skill first: the agent loads the skill, then follows it.

    dotnet run loop.cs .workitems/T01/task.md

    Open app/.workitems/T01/plan.md. Does it have the three sections? Does the plan select employees by number, not by name, as the technical notes in task.md ask?

  6. Undo the run. Your skills stay: they are in their own commit.

    git -C app reset --hard HEAD~1
Check

Lab 3 · 15 min

A quality gate the repository owns

Why

"All tests pass" from the agent is a claim, not proof. And an agent forgets: it may skip the build, run only the tests it just wrote, or leave out a check your team always does. So we don't trust the agent to remember. After every implement step, code runs the build, the entire test suite and every other check that must always pass on a change: a deterministic check, the same every time, whatever the agent did or said. Code decides. But which checks is not the harness's business: every repository has its own. So the harness runs a script in the root of the repository, quality-gate.ps1. Exit code 0 means green. The developers own the script, just like the skills.

  1. Write a first, simple gate.

    app/quality-gate.ps1
    # Quality gate of this repository. Exit code 0 = pass.

dotnet build
if ($LASTEXITCODE -ne 0) { exit 1 }

dotnet test --no-build
exit $LASTEXITCODE
    An example, not the finish line

    Build and test are only where this example starts, because that is all this small repository has. Your gate should check what your repository needs, and it grows with every mistake you want to stop for good: formatting with dotnet format --verify-no-changes, a security scan with Aikido, coverage thresholds, architecture rules, linters, a check that migrations run, a check that nothing outside the task's folders changed. Each check is a few more lines in this script, written by the team that owns the repository. The harness does not change: it only looks at the exit code.

  2. Try it by hand, from inside app/:

    cd app
pwsh ./quality-gate.ps1
echo $LASTEXITCODE
cd ..

  3. In loop.cs, run the gate after the implement step. Save its output in the work item folder, and stop before the commit when it fails.

    loop.cs, after the implement step
    var (exitCode, output) = Run("pwsh", "-NoProfile -File quality-gate.ps1", check: false);
File.WriteAllText(Path.Combine(repo, workItem, "gate-1.md"), output);
if (exitCode != 0)
{
    Console.WriteLine($"Quality gate FAILED, see {workItem}/gate-1.md. Nothing is committed.");
    return;
}

  4. Commit the gate:

    git -C app add quality-gate.ps1
git -C app commit -m "Add quality gate"

    Then run the loop on T01, and open app/.workitems/T01/gate-1.md:

    dotnet run loop.cs .workitems/T01/task.md

  5. Undo the run. If the gate failed, the loop did not commit: use the second command from Between runs instead.

    git -C app reset --hard HEAD~1

  6. Now read a failing gate. Break a test by hand: in app/tests/Payroll.Tests/WageTaxTests.cs, change 756.29m into 756.30m. Run the gate again and save what it prints:

    cd app
pwsh ./quality-gate.ps1 > ../gate-raw.txt
cd ..

    Open gate-raw.txt. Read it as if you are the agent that must fix this. How many lines are there? How many of them help? Keep the file and the broken test for Lab 4.

Lab 4 · 20 min

Feedback the agent can act on

Why

A red gate is only useful if the next attempt knows exactly what to fix. The gate's output is the next prompt. So write it like one: only the signal, where to look, and what to do and what not. Then let code send it back to the implement step, a limited number of times.

What good gate output contains

PropertyInstead ofWrite
Only the signalRestore, build and test runner noiseThe compiler errors, or the failing tests. Nothing else.
Where to lookAbsolute paths from the build machinetests\Payroll.Tests\WageTaxTests.cs:9, relative to the repository
What to do, and what notNothing: the agent guesses"Decide whether the code or the test is wrong. Fix the code unless the test contradicts the task. Never delete or weaken a test."

  1. Rewrite quality-gate.ps1 so that it prints instructions. Start from the reference below: copy it over your gate and read how it works. It uses dotnet test --logger trx: the TRX report is XML with each failing test, its message and its stack trace, which is much easier to filter than the console output. Then make the How to fix parts your own: write the instructions you would want if you had to fix this, and the rules your team cares about.

    Reference: quality-gate.ps1
    app/quality-gate.ps1
    # Quality gate of this repository. The development loop runs it after every implement step.
#   Exit code 0 = pass, anything else = fail.
#   Everything printed here goes to the agent that has to fix it, so write instructions, not a log.

$root = (Get-Location).Path + [IO.Path]::DirectorySeparatorChar
function Relative([string]$text) { $text.Replace($root, '') }

# 1. Build. Warnings count as errors in this repository (Directory.Build.props).
$build = dotnet build --nologo -v quiet -clp:NoSummary 2>&1 | ForEach-Object { "$_" }
if ($LASTEXITCODE -ne 0) {
    $errors = $build | Where-Object { $_ -match ': (error|warning) [A-Z]+\d+' } |
        ForEach-Object { Relative ($_ -replace '\s*\[[^\]]+\]\s*$', '') } | Sort-Object -Unique
    '# Quality gate: FAILED at build'
    ''
    'The code does not compile. Fix every error below.'
    ''
    if ($errors) { $errors | ForEach-Object { "- $_" } } else { $build | Select-Object -Last 30 }
    ''
    '## How to fix'
    ''
    '- Fix the cause in the code. Do not suppress warnings and do not delete code or tests to make an error go away.'
    '- Check your fix with `dotnet build`.'
    exit 1
}

# 2. Tests. The TRX report gives us each failing test with its message and location.
Remove-Item TestResults -Recurse -Force -ErrorAction SilentlyContinue
$test = dotnet test --no-build --nologo --logger 'trx;LogFileName=gate.trx' --results-directory TestResults 2>&1 | ForEach-Object { "$_" }
if ($LASTEXITCODE -eq 0) {
    '# Quality gate: PASSED'
    ''
    'The build is clean and all tests pass.'
    exit 0
}

$trx = Get-ChildItem TestResults -Recurse -Filter gate.trx | Select-Object -First 1
if (-not $trx) {
    '# Quality gate: FAILED at tests'
    ''
    'The test run did not finish. Its last output:'
    ''
    $test | Select-Object -Last 40
    exit 1
}

[xml]$report = Get-Content $trx.FullName -Raw
$failed = @($report.TestRun.Results.UnitTestResult | Where-Object outcome -eq 'Failed')
$total = $report.TestRun.ResultSummary.Counters.total

'# Quality gate: FAILED at tests'
''
"$($failed.Count) of $total tests fail."
foreach ($t in $failed) {
    $message = ($t.Output.ErrorInfo.Message -split "`r?`n" | ForEach-Object { "    $_" }) -join "`n"
    $frame = $t.Output.ErrorInfo.StackTrace -split "`r?`n" | Where-Object { $_ -match ' in (.+):line (\d+)' } | Select-Object -First 1
    $location = if ($frame -match ' in (.+):line (\d+)') { "$(Relative $Matches[1]):$($Matches[2])" } else { 'unknown' }
    ''
    "## $($t.testName)"
    ''
    "- Where: ``$location``"
    '- What failed:'
    ''
    $message
}
''
'## How to fix'
''
'- For each failing test, decide whether the code or the test is wrong.'
'- Fix the code when it does not do what the task asks. Change a test only when it contradicts the task.'
'- Never delete, skip or weaken a test to make it pass.'
exit 1

// Runs the repository's quality gate. Returns null when green, otherwise the file with the instructions for the agent.
string? QualityGate(int attempt)
{
    var (exitCode, output) = Run("pwsh", "-NoProfile -File quality-gate.ps1", check: false);
    var file = $"{workItem}/gate-{attempt}.md";
    File.WriteAllText(Path.Combine(repo, file), output);
    Console.WriteLine($"Quality gate: {(exitCode == 0 ? "passed" : "FAILED")}, see {file}");
    return exitCode == 0 ? null : file;
}

Lab 5 · 20 min

Agentic review

Why

The gate only sees what the tests see. Is every requirement in task.md implemented? Are the error cases tested? Did the change stay in scope? That needs a reviewer: a fresh session that did not write the code. The review itself is free text, for humans. But the loop needs a decision. So after the review, a follow-up message in the same session asks for the findings as data: severity, and one line each. Code reads that and decides.

  1. Create the review skill. It defines what to check, what high, medium and low mean, and what goes into the JSON the harness asks for afterwards. All of that belongs to the repository. The harness only owns the shape of the JSON. A longer version is in solution/app/.github/skills/review/.

    app/.github/skills/review/SKILL.md
    ---
name: review
description: Reviews the uncommitted changes for a work item. Use when invoked as /review <work item folder>.
argument-hint: <work item folder>
---

# Review a work item

The argument is a work item folder with `task.md` and `plan.md`. You review; you do not change any file.
The quality gate has passed: do not run the build or the tests.

1. Read `task.md` and `plan.md`.
2. See what changed: `git status --short` and `git diff HEAD`. Read new files in full. Ignore `.workitems/`.
3. Check that every requirement and example in `task.md` is implemented exactly, that error cases are
   handled and tested, and that nothing outside the task changed.

Severity:
- **high**: a requirement is missing or wrong, or there is a bug.
- **medium**: fix before a human reviews it: a missing test, an unhandled edge case, a change outside the task.
- **low**: a matter of taste. Fine to merge without it.

Reply with the review in Markdown: your verdict, then one section per finding.

## Findings as JSON

When the harness asks for your findings as JSON: one finding per problem from your review, the low ones too,
explained in a single line. Return an empty list when there is nothing to fix.

  2. At the top of loop.cs, under the #:property line, allow the experimental typed reply, and add three usings:

    loop.cs, top
    #pragma warning disable GHCP001   // typed replies are experimental in the SDK

using System.Text.Encodings.Web;
using System.Text.Json;
using System.Text.Json.Serialization;

  3. Add the review step and the shape of its result. Both messages carry no instructions: the first calls the skill, the second only asks for the JSON. SendAndWaitAsync<ReviewResult> derives a JSON schema from the records, sends it along with the message, and gives you a typed object back.

    loop.cs, next to QualityGate
    // The review skill writes the review. A follow-up in the SAME session turns it into data.
async Task<string?> Review(int attempt)
{
    Console.WriteLine($"--- review-{attempt}: started");
    var timer = Stopwatch.StartNew();
    await using var session = await NewSession();
    var review = await session.SendAndWaitAsync($"/review {workItem}", TimeSpan.FromMinutes(30));
    File.WriteAllText(Path.Combine(repo, workItem, $"review-{attempt}.md"), review?.Data.Content);

    var result = await session.SendAndWaitAsync<ReviewResult>("Your findings as JSON.", timeout: TimeSpan.FromMinutes(5));

    var file = $"{workItem}/review-{attempt}.json";
    var json = new JsonSerializerOptions { WriteIndented = true, Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping };
    File.WriteAllText(Path.Combine(repo, file), JsonSerializer.Serialize(result, json));
    var blocking = result!.Findings.Count(f => f.Severity is Severity.High or Severity.Medium);
    Console.WriteLine($"--- review-{attempt}: finished in {timer.Elapsed:m\\:ss}, {result.Findings.Count} findings, {blocking} high or medium, see {file}");
    return blocking > 0 ? file : null;
}
    loop.cs, at the very end of the file
    record ReviewResult(List<Finding> Findings);
record Finding(Severity Severity, string Summary);
[JsonConverter(typeof(JsonStringEnumConverter<Severity>))] enum Severity { High, Medium, Low }

        feedback = QualityGate(attempt);
    if (feedback is not null) continue;

Lab 6 · 10 min

Observability

Why

Every run of the loop should leave a record of what it actually did, not only what the agent says it did. That record is a necessary artifact of every run, next to the plan, the gate results and the reviews. You need it to trace a run step by step, and the improvement loop in Lab 7 reads it to find where the loop is weak. The SDK emits an event for everything: the skill that was invoked, every tool call and its output, every model call with its tokens. One line of code writes them all, into the work item folder, where they are committed with the rest of the evidence.

  1. Give NewSession a step name, and write every event of that step as one JSON line in the work item folder. Note the braces: NewSession becomes a method body instead of a single => expression. The second console line shows every tool call that failed, or that something refused.

    loop.cs
    async Task<CopilotSession> NewSession(string step)
{
    var log = Path.Combine(repo, workItem, $"{step}.events.jsonl");
    var gate = new object();
    return await client.CreateSessionAsync(new SessionConfig
    {
        // ... Model, WorkingDirectory, and so on, as before ...
        OnEvent = e =>
        {
            lock (gate) File.AppendAllText(log, e.ToJson() + "\n");
            if (e is ToolExecutionStartEvent t) Console.WriteLine($"  {step}: {t.Data.ToolName}");
            if (e is ToolExecutionCompleteEvent { Data.Success: false } c) Console.WriteLine($"  {step}: FAILED {c.Data.Error?.Message}");
        },
    });
}

    Pass the step name where it is called. Ask already has one (plan, implement-1, ...); in Review, use the attempt:

    loop.cs, in Ask
    await using var session = await NewSession(step);
    loop.cs, in Review
    await using var session = await NewSession("review-" + attempt);

  2. Run the loop on T01. Then ask the logs a question: what did each step cost?

    dotnet run loop.cs .workitems/T01/task.md
    Get-ChildItem app/.workitems/T01/*.events.jsonl | ForEach-Object {
    $events = Get-Content $_ | ConvertFrom-Json
    $usage  = $events | Where-Object type -eq 'assistant.usage'
    [pscustomobject]@{
        Step       = $_.Name -replace '\.events\.jsonl$', ''
        ModelCalls = $usage.Count
        ToolCalls  = ($events | Where-Object type -eq 'tool.execution_start').Count
        InTokens   = ($usage.data.inputTokens  | Measure-Object -Sum).Sum
        OutTokens  = ($usage.data.outputTokens | Measure-Object -Sum).Sum
    }
} | Format-Table

  3. Undo the run. The logs go with it: they were part of the commit.

    git -C app reset --hard HEAD~1

Lab 7 · 20 min

The improvement loop

Why

Every run leaves evidence: the task, the plan, every gate result, every review, and the full event log. So far that evidence answered one question: was this work item done well? It can also answer a second one: where is the loop itself weak? A retry that a clearer skill would have prevented, a review finding the gate could have caught, a rule the agent tried to break, a command it ran ten times: each of those is something to engineer away. An agent can do the reading and propose changes to the skills, the gate and the hooks. That is not a step of the harness. You run it yourself, in an interactive session, and you decide which changes go in, with a normal pull request. That outer loop is how trust grows over time.

the loop runs work items› evidence in the work item folders› you + /improve, interactive› you pick: pull request on skills, gate, hooks› better runs
The outer loop, outside the harness. The agent proposes; the people who own the rules decide.

Menu B · 15 min

Guardrails

The agent may still do anything: ApproveAll. The implement skill asks it not to touch the task, the skills or quality-gate.ps1, but that is only an instruction. Make the rule hard with a hook. Copilot runs a preToolUse hook before every tool call; the hook sees the tool and its arguments and can deny the call, with a reason that goes back to the agent. The hook lives in the repository, next to the rules it protects, and owned by the same developers. It works in every Copilot session in the repository: the loop, and a developer working by hand. loop.cs does not change.

  1. Register the hook. Copilot loads every JSON file in .github/hooks/.

    app/.github/hooks/guard.json
    {
  "version": 1,
  "hooks": {
    "preToolUse": [
      {
        "type": "command",
        "bash": "pwsh -NoProfile -File .github/hooks/guard.ps1",
        "powershell": "pwsh -NoProfile -File .github/hooks/guard.ps1",
        "cwd": ".",
        "timeoutSec": 15
      }
    ]
  }
}

  2. Write the guard. It reads the tool call from standard input. No output means the call goes ahead.

    app/.github/hooks/guard.ps1
    # Guardrail of this repository. Copilot runs it before every tool call, in every session in this repository:
# the development loop and a developer working by hand alike.
# Input (stdin): one JSON object with toolName and toolArgs. Output: nothing to allow, or a deny with a reason for the agent.
$call = [Console]::In.ReadToEnd() | ConvertFrom-Json
$tool = if ($call.toolArgs -is [string]) { $call.toolArgs | ConvertFrom-Json } else { $call.toolArgs }

function Deny([string]$reason) {
    @{ permissionDecision = 'deny'; permissionDecisionReason = $reason } | ConvertTo-Json -Compress
    exit 0
}

# The rules are owned by the developers: the task, the skills, the hooks and the quality gate.
$path = "$($tool.path)" -replace '\\', '/'
if ($call.toolName -in 'create', 'edit' -and $path -match '/(task\.md|quality-gate\.ps1)$|/\.github/') {
    Deny "$($tool.path) is owned by the developers. Change the code, not the rules."
}

# The harness commits, after the gate and the review.
if ($call.toolName -in 'bash', 'powershell' -and "$($tool.command)" -match 'git\s+(commit|push)') {
    Deny 'The harness commits. You only change files.'
}

  3. Commit the hook, then test it with a work item that asks for the wrong thing. Create app/.workitems/T90/task.md:

    app/.workitems/T90/task.md

Menu C · 10 min · after Lab 6

OpenTelemetry

The event log from Lab 6 is the SDK's own format. OpenTelemetry is the standard: a span for every agent turn, model call and tool call, with tokens and durations, which any tracing backend can read. Write those spans per step as well, next to the events.

  1. Telemetry is set on the client, which starts its own Copilot runtime, not on the session. So each step gets its own client; that costs less than a second per step. Delete the lines at the top that create and start the client, add NewClient, and give NewSession the client as its first parameter:

    loop.cs
    // One Copilot runtime per step, so every step gets its own OpenTelemetry file.
async Task<CopilotClient> NewClient(string step)
{
    var client = new CopilotClient(new CopilotClientOptions
    {
        Telemetry = new TelemetryConfig { ExporterType = "file", FilePath = Path.Combine(repo, workItem, $"{step}.otel.jsonl") },
    });
    await client.StartAsync();
    return client;
}

async Task<CopilotSession> NewSession(CopilotClient client, string step)

  2. In Ask and Review, create the client before the session. await using stops the runtime at the end of the step, and that is when it finishes writing its file:

    loop.cs, in Ask
    await using var client = await NewClient(step);
await using var session = await NewSession(client, step);
    loop.cs, in Review
    await using var client = await NewClient("review-" + attempt);
await using var session = await NewSession(client, "review-" + attempt);

  3. Run a work item and open plan.otel.jsonl: one JSON object per line, with spans like invoke_agent, chat <model> and execute_tool <tool>. Each implement attempt has its own file, like its event log. For a real backend, set OtlpEndpoint instead of a file, for example a local Aspire dashboard or Jaeger.

Menu D · read, then try if you like

Tools and MCP

Skills tell the agent how to work. Tools decide what it can do. A typed tool is narrower and more predictable than "run any shell command".

  • MCP servers plug in existing tool sets. Useful ones: the Playwright MCP server (drive a browser: let the reviewer open the payslip page and try the dropdown of T01 for real, instead of trusting the tests), the GitHub MCP server (issues, pull requests), and database or documentation servers.
  • Your own C# functions become tools with CopilotTool.DefineTool, built on Microsoft.Extensions.AI.
  • Microsoft Agent Framework wraps a Copilot client as an AIAgent (package Microsoft.Agents.AI.GitHub.Copilot, copilotClient.AsAIAgent(...)), so you can combine Copilot with other agents and add your own tools in a framework-standard way.
loop.cs, in the SessionConfig of NewSession (add using System.ComponentModel; at the top)
McpServers = new Dictionary<string, McpServerConfig>
{
    ["playwright"] = new McpStdioServerConfig { Command = "npx", Args = ["@playwright/mcp@0.0.85"], Tools = ["*"] },
},
Tools =
[
    CopilotTool.DefineTool(
        [Description("Returns the task description of a work item.")]
        (string workItem) => File.ReadAllText(Path.Combine(repo, workItem, "task.md")),
        factoryOptions: new() { Name = "get_task" }),
],
Two things to decide first
  • A Playwright reviewer goes against two rules in app/AGENTS.md: interaction is checked in the browser by a human, and an agent never starts the app. Changing those rules is a decision for the repository's owners, not for the harness. The reviewer would also have to start the app and stop it again.
  • Pin the version of every MCP server, as above. With @latest and ApproveAll, any new release of the server runs on your machine with every tool call approved.

Which shell commands does your agent run again and again? Which of them would be safer and cheaper as one typed tool?

10 min

Wrap-up: and then a human looks

The loop ends with a commit (on its own branch, once you add menu A). In real life it goes one step further: push the branch and open a merge request on GitHub or GitLab. That is where the human review happens, in the tool your team already uses. The work item folder travels along: the reviewer sees the task, the plan, every gate result and the agent's review next to the diff.

  • Push and open the merge request: two more Run lines (git push -u origin workitem/{id}, and gh pr create or the GitLab CLI). Left out today on purpose.
  • A second loop for review comments: another small harness can follow up on the merge request. It reads new comments, writes them as a feedback file into the work item folder, calls /implement with it, runs the gate and the review, and pushes again. Same skills, same gate, different trigger.

For your own repository, in this order

  1. Write down how your team works as skills: plan, implement, review. Commit them.
  2. Write the quality gate as a script in the repository. Make its output an instruction, not a log.
  3. Keep the harness small and generic: it calls skills and the gate, loops a limited number of times, and decides.
  4. Put the evidence where the reviewer is: a work item folder, a branch, a merge request.
  5. Every time the agent gets something wrong, fix the skill, the gate or a hook, so it cannot happen again. Let an agent find those moments for you, and let people decide on the fix.
